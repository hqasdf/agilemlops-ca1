The user confirmed the MLflow UI loads at `http://mlflow-pbi12.eba-9bnrxizu.us-east-1.elasticbeanstalk.com`; an automated pipeline connection and artifact retrieval have not been verified.

The three synthetic files in `practice/pbi10/` are for an isolated rehearsal database only; do not insert synthetic rows into `amlops_ca1`. They contain 120 linked records across multiple order dates, with both label classes. The URLs can be passed to the command without modifying source.

## Setup and remaining checks

1. Install the pinned team dependencies and `requirements-pbi10.txt` in a project-specific virtual environment. This branch has not been tested in that complete environment. Never put passwords in code, version control, command history or screenshots.
2. Verify the original full historical order snapshot and create the sealed order-key manifest from it, before any new batch is admitted. The helper `src.pbi10_holdout.build_sealed_keys` hashes country-qualified order keys dated from 14 April 2023. A local manifest was generated from the original cleaned historical CSV (949,889 unique orders; 144,126 sealed keys), but its provenance and persistence need team verification before operational use. A file's valid hash format alone does not prove the manifest is complete.
3. Use a durable, initially empty new-order ledger whose location is controlled by the operator. Preserve it across batches. The command currently stores ledger keys after committing the database transaction; if the process stops between those steps, reconciliation is required. Do not run concurrent batches with the same ledger.
4. Supply `CA1_DB_HOST`, `CA1_DB_PORT` (optional), `CA1_DB_USER`, `CA1_DB_PASSWORD`, `CA1_DB_NAME`, `CA1_DB_SSL_CA`, and `MLFLOW_TRACKING_URI` as environment variables. Connection settings must point to a disposable MySQL rehearsal database for synthetic data. The selected user must have only the access required for staging and inserts. RDS TLS certificate and hostname verification are enabled.
5. Exercise URL download, cleaning, schema validation, staging, repeat batch, conflicts and rollback on the disposable database. Verify actual live types, keys, counts and stored representations. The historical/new order ledger and database must remain consistent; the current implementation is not proven crash-safe.
6. Confirm the selected holdout split is valid for the actual batch. The code chooses a validation boundary within the current labelled batch and retains earlier current rows for training. Nithish's calibration set excludes current-batch fit rows, so calibration dates can precede some fit dates; document this caveat. Tiny or single-date batches can fail, and a two-class validation set is required by the model routines.
7. Verify each member's actual routine can train and publish retrained models and artifacts to the shared MLflow server. The extracted Ephraim module uses settings recorded in the committed notebook; reconcile it with Ephraim's uncommitted local notebook/module before integration. Confirm run IDs and model artifacts can be retrieved.
8. Record complete wall-clock duration, including URL download, database work, training and artifact uploads. The three-minute target is unverified. Complete PBI 4 #27 only when historical and newly accepted data are demonstrably available to both analytics and training.

The current focused tests use synthetic data and mocks. They do not prove production or live AWS behavior, performance, database atomicity under concurrency, or compatibility with the full pinned environment.
